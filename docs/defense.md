# Шпаргалка к защите

## План выступления (7–8 минут)

**1. Что это (30 с).** «Мультиагентная система на локальной open-source модели играет во Freeciv — открытый аналог Civilization. Цель — первые 50 ходов: выжить, вырасти, набрать очки. Это удобный полигон: объективный счёт, решения разного масштаба, партию можно повторить».

**2. Архитектура (1,5 мин).** Схема из `report.md`, раздел 2. Главное:
- правитель → советники → исполнитель;
- исполнитель — **код, а не LLM**: проверяет каждое действие по списку допустимых от игры;
- каждый советник видит только свой срез и командует только своими юнитами.

**3. Модель и ограничения (1 мин).** RTX 3050, 4 ГБ, qwen3:4b-instruct. Чтение ~1160 ток/с, генерация ~15–18 ток/с → 6–15 вызовов на ход за 60 с. Thinking против instruct: 25,8 с против 1,5 с при одинаковом результате.

**4. Демо (1,5 мин).** Запустить партию на 3–5 ходов, показать вывод по ходам, `metrics.json`, трейс в Grafana.

**5. Память, скиллы, знания (1 мин).** Таблица слоёв памяти; скиллы — код, дающий подсказки; рефлексия пишет уроки.

**6. Evals (1 мин).** Таблица из `report.md`, раздел 9. Говорить честно и в таком порядке:
- иерархия против одного агента: недопустимых действий 14–21% против **48%**, ошибок формата 0–3% против **13%**, самый долгий ход 11–15 с против **40 с**. Это подтверждает выбор архитектуры;
- цена — в ~1,6 раза больше вызовов и на 25–40% больше токенов;
- **по счёту на 15 ходах разницы нет** (2–4 очка, random тоже 3): горизонт слишком короткий, партий по 1–2. Как сделать вывод значимым — 50 ходов × 5 партий, скрипт готов, упирается во время.

**7. Изоляция и observability (1 мин).** Все 4 компонента в Docker; агент — не root, без capabilities, с лимитами (показать `touch /etc/pwned` → Permission denied). Почему не Firecracker/Kata (GPU + нет KVM в WSL2); главная защита от ошибок модели — валидатор действий. Трейсы, метрики, логи, алерты в otel-lgtm.

**8. Находки (30 с).** Тег thinking в Ollama; повторный выбор исследования обнуляет прогресс; сервер обрывает партию на ~90-м ходу; `LLMWrapper` ломает действия науки.

## Команды для демо

```
docker start freeciv-web
docker compose up -d                       # ollama (+ otel-lgtm)
CIV_OTEL=1 uv run python scripts/play.py --turns 5
uv run python -m civ_agents.observability.summary runs/<папка>
cat runs/<папка>/metrics.json
```
Grafana: http://localhost:3000 → Explore → Tempo (трейсы), Prometheus (`civ_*`), Loki (логи).

**Если `freeciv-web` пропал** (`docker ps` его не показывает — бывает после перезапуска Docker/WSL): `uv run start_freeciv_web_service`. Останавливать только `docker stop freeciv-web`.

Демо в контейнере: `docker compose --profile agent run --rm agent --turns 3`.

**Заранее** запусти сервер и прогрей модель (`uv run python -m civ_agents.llm "ok"`): холодный старт модели — до 46 с, сервера игры — ~15 с.

## Вероятные вопросы и ответы

**Почему именно иерархия, а не один агент?**
Маленькой модели проще узкая задача с коротким промптом. Каждый советник видит свой срез и командует своими юнитами. Роутинг вызывает советника, только если у него есть работа, поэтому вызовов немного: 2–4 за ход. Один агент реализован (`--mode single`) и сравнивается в evals.

**Зачем исполнитель-код? Почему не дать модели отправлять действия напрямую?**
Допустимость действия — детерминированный вопрос, на него отвечает сама игра (`available_actions`). Модель может ошибиться в имени или id, а неверная команда в CivRealm роняет всю партию. Исполнитель гарантирует: в игру попадает только допустимое. Это и есть основная изоляция от ошибок модели.

**Что если модель ответит не JSON?**
Разбор терпит обёртку ```json и текст вокруг. При ошибке модели возвращается текст ошибки с перечнем допустимых действий и делается один переспрос. Если и он не удался, советник в этот ход ничего не делает: партия не падает. Доля ошибок формата — метрика в evals.

**Почему qwen3:4b, а не больше?**
4 ГБ видеопамяти, из них ~1,3 ГБ занимает Windows. 7–8B частично ушли бы на CPU и были бы в разы медленнее. Instruct-версия, потому что thinking в 17 раз медленнее при том же результате на наших задачах.

**Почему не vLLM?**
vLLM рассчитан на серверные GPU с большим объёмом памяти и высокую параллельную нагрузку. У нас 4 ГБ и один запрос за раз — Ollama проще и подходит.

**Почему Docker, а не gVisor/Firecracker?**
Модели нужен GPU, а Kata и Firecracker требуют KVM, которого нет в WSL2. Главная угроза у нас — не выполнение чужого кода (агенты код не генерируют), а неверные действия модели; от неё защищает валидатор. Если появится агент, пишущий код, он будет выполняться в контейнере с gVisor (`runsc`), без сети и с read-only ФС.

**Агенты в контейнере?**
Да, все четыре компонента в контейнерах. Агент — непривилегированный пользователь uid 1000, все capabilities сняты, `no-new-privileges`, лимиты 4 ГБ / 4 CPU / 512 процессов, писать может только в `runs/` и `knowledge/`. Проверял: `touch /etc/pwned` → Permission denied, партия в контейнере идёт так же, как снаружи (`docs/img/agent_container_*.png`).

**Какое у контейнера агента слабое место?**
Сеть хоста (`network_mode: host`): CivRealm ходит на сервер по `localhost` и открывает новые клиентские порты на каждую партию. Значит, контейнер видит все локальные порты. Исправление — общая внутренняя сеть compose (`internal: true`) с сервером игры и моделью по именам сервисов, без выхода в интернет. Требует поправить адрес сервера в конфиге CivRealm — следующий шаг.

**Почему в контейнере агента не read-only ФС?**
CivRealm пишет свои логи внутрь пакета (в `.venv`). Можно включить `read_only: true` и смонтировать для этого каталога tmpfs; сейчас вместо этого запись ограничена правами пользователя: системные каталоги ему недоступны.

**Как устроена память? Почему BM25, а не эмбеддинги?**
Четыре слоя: рабочая (промпт), эпизодическая (события из разницы состояний), семантическая (поиск по `.md`), рефлексия (уроки после партии). BM25, потому что база маленькая и терминологическая (Settlers, Grassland), а вторая модель для эмбеддингов не поместилась бы в видеопамять. Недостаток — нет синонимов; улучшение — гибридный поиск.

**Почему не MemGPT/Letta/Mem0/GraphRAG?**
Letta требует, чтобы модель сама управляла памятью, — много служебных вызовов, 4B-модель с этим плохо справляется и не уложится в бюджет хода. Mem0 рассчитан на диалоги с пользователем. GraphRAG строит граф с помощью LLM — дорого и избыточно для 50 ходов. Подробно — `report.md`, раздел 8.

**Откуда события эпизодической памяти? Не галлюцинирует ли модель?**
События выводит код из разницы состояний между ходами (появился город, пропал юнит, изучена технология). Модель их не пишет, поэтому галлюцинаций нет.

**Что такое скиллы у вас?**
Детерминированные процедуры поверх состояния: оценка места для города, следующая технология, оценка угроз. Их результат — подсказка в промпт; решение остаётся за моделью, исполнение — за исполнителем. Описание каждого — в `skills/*.md`.

**Как вы оцениваете LLM?**
Вопросы по правилам с проверкой кодом (без LLM-судьи — на 4B он сам ошибается), без памяти и с RAG. Плюс по реальным партиям: доля разборчивых JSON, доля допустимых действий.

**Как вы оцениваете систему?**
Счёт, города, население, выживание на фиксированном горизонте; время и токены на ход; несколько партий на вариант со средним и разбросом; сравнение с random; аблации (без памяти, без скиллов, один агент).

**Ваш агент не лучше случайного по счёту — зачем тогда LLM?**
Да, на 15 ходах счёт одинаковый, и я этого не скрываю. За 15 ходов очки почти не растут: они идут от граждан и технологий, а стартовые поселенцы и у random стоят на годных клетках. Метрики качества решений при этом различаются сильно: в иерархии модель гораздо реже предлагает невозможное и не ломает формат. Утверждение «играет лучше» требует 50+ ходов и 5+ партий на вариант; инфраструктура для этого готова, не хватило времени на ноутбуке (~3–5 минут на партию в 15 ходов).

**Почему без памяти вышло лучше?**
Одна партия против одной — это шум, вывода из неё не сделать. При этом сам RAG работает: на вопросах по правилам точность растёт с 25% до 83%. Просто в первые 15 ходов знание правил не узкое место. Гипотезы: на 15 ходах эпизодической памяти ещё нечего дать, а ~300 токенов заметок отвлекают 4B-модель. Проверить можно той же аблацией на длинных партиях. Если подтвердится — сделать заметки короче и подключать их по событию, а не каждый ход.

**83% с RAG — не подгонка ли это? Вы же сами писали и вопросы, и базу знаний.**
Отчасти да, оценка оптимистичная: формулировки близки, и BM25 легко находит фрагмент. Но и проверяет этот eval именно это: умеет ли система достать нужное знание и использовать его. Без памяти модель отвечает на 25%, путая Freeciv с Civilization. Улучшение — независимый набор вопросов по вики Freeciv и проверка на перефразированных вопросах.

**Почему одна партия, а не несколько?**
Каждая партия — минуты на ноутбуке, а одна потерялась при зависании WSL. Поэтому в таблице столбец «Партий»: видно, где одна, где две. Разброс я считаю там, где партий больше одной.

**Почему фиксированный горизонт?**
Сервер сам завершает партию около 90-го хода, а случайный агент может погибнуть раньше. Партии разной длины несравнимы, поэтому длину задаёт сессия (N ходов).

**Почему несколько партий?**
Разброс большой: встроенный ИИ набирал от 80 до 131 очков в разных партиях. Одна партия ничего не доказывает.

**Что показывают метрики и трейсы?**
Трейс хода: какие агенты вызывались, сколько длился каждый вызов модели, сколько токенов, были ли ошибки. Метрики: время хода, вызовы и задержка модели по агентам, токены, принятые и отклонённые действия, состояние партии. Логи — в Loki.

**Какие алерты?**
Ход дольше 80% бюджета (зависание), ошибки модели, доля недопустимых действий выше 30%, ход без действий. Пишутся в `alerts.jsonl`, лог и метрику `civ_alerts`; в Grafana на неё вешается уведомление. Видеопамять не отслеживается — нужен экспортер `nvidia-smi`, это следующий шаг.

**Зачем алерт в Grafana, если есть `alerts.py`?**
`alerts.py` работает внутри процесса агента и ловит проблемы конкретного хода (долгий ход, ошибки модели, много недопустимых действий). Если процесс упал или завис намертво, сам он ничего не сообщит. Правило в Grafana смотрит снаружи: если за 5 минут не было ни одного действия, агент встал. Так устроен мониторинг и в продакшне: проверка снаружи, а не самодиагностика.

**Что видно по трейсу?**
На самом долгом ходе (12 с) 6,8 с ушло на вызов модели экономистом, 3,6 с — военным, на исполнитель около 1 с. Узкое место — генерация ответа экономиста. Распараллеливать советников бессмысленно: Ollama на 4 ГБ выполняет один запрос за раз. Ускорить можно только короче промпт или ответ.

**Что было самым сложным?**
Интеграция с CivRealm: зависимости 2023 года (Python 3.10, старый ray, setuptools<81), неочевидное завершение партии (сервер обрывает на ~90-м ходу), `LLMWrapper`, переводящий имена всех действий и ломающий науку. Каждая находка — в ADR.

**Что бы вы улучшили?**
Контейнер агента во внутренней сети вместо сети хоста; гибридный поиск в памяти; проверка уроков рефлексии; больше партий в evals; модель побольше на сервере с GPU; структурированный вывод через JSON-схему сервера (response_format) вместо разбора текста.

**Как переключить модель?**
Профиль в `configs/settings.yaml` или переменная `CIV_LLM__ACTIVE_PROFILE=local_thinking`. Слой модели отделён интерфейсом, код агентов не меняется.

**Как воспроизвести партию?**
Папка прогона содержит снимок настроек `config.yaml`, состояния по ходам, действия, журнал вызовов модели; сид игры фиксирован в конфиге CivRealm.
