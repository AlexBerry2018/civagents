# Замеры сервера модели

Условия: RTX 3050 Laptop 4 ГБ (~1,3 ГБ занято Windows), Ollama в Docker (WSL2),
qwen3:4b-instruct (Q4_K_M), контекст 8192, KV-кэш q8_0, flash attention,
размещение 20/80 CPU/GPU. Модель уже загружена (load ≈ 0).
Промпт — фрагменты пакетов сервера Freeciv (~2,2 символа на токен).

| 3648 | да  | 0,06 с | 38 ток, 17,3 ток/с | 2,3 с |

Холодный старт: загрузка модели ~25 с; первые запросы после загрузки
заметно медленнее (207 ток/с чтение, 6,4 ток/с генерация).

Thinking vs instruct (простой вызов инструмента, ~200 ток промпта):
- qwen3:4b (thinking) — 392–515 ток ответа, 16–21 с;
- qwen3:4b-instruct — 35 ток, ~1,5 с.

## Выводы

- Чтение промпта ~1160 ток/с: 1000 токенов состояния ≈ 0,9 с.
- Генерация ~15–18 ток/с: каждый токен ответа ≈ 60 мс,
  ответ на 80 токенов дороже чтения 3,6k промпта.
- Генерация замедляется с ростом контекста (17,8 → 14,2 ток/с).
- Кэш промпта сокращает вызов в 3–4 раза.
- Бюджет хода: вызов 3–10 с → при лимите 60 с на ход ~6–15 вызовов.
- Сырые данные игры дорогие (~2,2 символа/токен) → нужна компактная сводка.
- Ответ модели должен быть коротким (JSON-действие, без пояснений).
- При замерах нужно контролировать кэш: общий префикс искажает результат.

## Как повторить

Функция `bench` (jq + curl к `/api/chat`), фрагменты из лога CivRealm:
`grep "Receiving packet" <лог> | sed -n '<диапазон строк>p' | head -c <байт>`.
Для замера без кэша каждый раз брать новый диапазон строк.


## Старт модели

| Ситуация | Время |
|---|---|
| Холодный старт: модель читается с диска (после перезагрузки) | 25–46 с |
| Повторная загрузка: файлы в кэше ОС, контейнер перезапущен | ~5 с |
| Модель уже в видеопамяти | ~0,1 с |

Перед партией модель прогревается (`warmup()`, таймаут 180 с).
